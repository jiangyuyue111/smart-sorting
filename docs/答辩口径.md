# 答辩口径

> 面向中期汇报/现场讲解。硬件未到位时怎么讲，讲什么，不说什么。
>
> **一条总原则**：不要藏"没有硬件"，要把它说成"我们把不确定性管起来了"。
> 评委见过太多"做出来了"和"数字很漂亮"，真正稀有的是**每个数字都能说出出处**。

---

## 一、90 秒开场（照着背）

> 这是分拣装置的上位机软件。硬件还在装配，所以现在跑的是模拟 MCU 加合成托盘图。
> 我演示三件事。
>
> **第一，识别。** 托盘上 12 件货随机摆，形状颜色都不同。程序自己框出来，
> 12 件全部判对，定位误差 0.31 毫米。
>
> **第二，排程。** 规则只要求"同形同色进同一个盒"，没要求顺序，所以这是个
> 旅行商问题。我们算了三种排法取最短的，12 件从 3576 毫米降到 3364 毫米。
>
> **第三，屏幕。** 规则要求每分拣一件就刷新序号、名称、图片、总数。这些是我们
> 真实渲染出来的帧，480×320，和真机上同一份代码。
>
> 有一点我先讲清楚：**这个 50.8 秒的节拍是按齿轮传动公式算出来的，不是实测。**
> 报告第 0 节把这四个数字的来源都列出来了——哪些是合成图结果、哪些是解析估算、
> 哪些是真几何量，一眼能看出来。实物装好后把参数填进去，它们才会变成实测值。

讲完这段，主动权就在你手里了。

## 二、三个必被问到的

### Q1「硬件呢？是不是只做了软件？」

**要说的：**

> 在装配。我们没有等硬件才开始写软件，因为软硬之间只有两个硬接口：
> **串口协议**和**标定矩阵**。
>
> 协议在树莓派侧和固件侧各实现了一遍，两边都有测试（Python 99 个用例、
> 固件 124 条断言），差错分支逐条对得上。
>
> 固件里跟硬件无关的部分——协议解析、梯形速度曲线、指令状态机——**已经写完
> 并全部测过**；跟硬件相关的 HAL 部分只有骨架，等板子。
> 这个分界在 `firmware/README.md` 里列了 7 条待办，没有含糊。
>
> 标定有独立工具，求解器自检的偏移是 1e-11 毫米，说明换算链路本身没算错。
>
> 所以硬件到位后，需要做的是**填参数、跑一次标定**，代码不用改。

**不要说的：** "软件部分已经全部完成了"——固件的脉冲部分还没上板，
被追问一句就崩。

### Q2「这个 50.8 秒靠谱吗？」

**要说的：**

> 不靠谱成实测值，这是解析估算——按齿轮传动公式算的，不含加减速、
> 回程间隙、相机曝光，所以真机只会更慢。
>
> 但它能给两个确定的结论：
> **一是量级**，180 秒预算下每件 15 秒，目前看很宽裕；
> **二是瓶颈在哪**——Z 轴占了运动时间的 46%，不是 XY。这个结论在真机上
> 依然成立，所以我们已经知道优化该往哪使。

这个回答的妙处：承认了不确定，但给出了**不确定之外仍然成立的结论**。

### Q3「你们和别的队比，有什么不一样？」

**不要吹首创。** 说三件具体的：

> 一，**所有参数在配置文件里**。现场抽签换货，只需要改判据文件，不改代码。
> 因为我们用的是形状几何特征加色相聚类，不是训练好的模型，所以没有"没见过的
> 类别"这个问题。
>
> 二，**失败分支是完整的**。夹空了就不往料盒跑、不停机——规则里卡住一件会
> 丢掉整轮，这个代价比少抓一件大得多。
>
> 三，**每个数字标了来源**。哪些能当实测、哪些不能，报告里直接写。

## 三、可能被追问的

| 问题 | 答法 |
|---|---|
| 抽签抽到没见过的货怎么办？ | 不用训练模型。判据是圆度、顶点数、色相区间，现场填进 `classes.json` 就行 |
| 现场光照不一样怎么办？ | 分割用的是明度通道 Otsu 自动找阈值，不是固定阈值；颜色取的是色相直方图**峰值**，取均值会被污渍带偏 |
| 为什么不用 YOLO？ | 两个原因：一是规则要求现场抽签，预训练模型的固定类别直接不成立；二是 15 秒/件的节拍里没有重试余量，识别只在开赛前跑一次，用不上实时推理 |
| 夹爪怎么知道夹到了？ | 用步进驱动器的堵转检测。空夹会一直合到底，夹到件会停在工件宽度处，**用停住的位置判断**，不是用力传感器——省一路传感器和一根线 |
| 万一通信断了？ | 两道独立超时：上位机 15 秒是防 MCU 死掉，固件几百毫秒是防某根轴被卡住。夹爪超时**不停机**，抬起来跳过 |
| 为什么排序只省了 5.9%？ | 因为每件"取点→料盒"那一段大约 200 毫米是固定的，排序只能优化取点之间和料盒之间。真正的节拍杠杆在 Z 轴，不在排序 |
| 节拍最快能压到多少？ | 现在 50.8 秒。最容易的一步是把 `z_safe_mm` 从假定的 45 mm 降到夹爪实际长度，其次是提 Z 轴速度——文件里改一个数就能试，不用动代码 |

## 四、四条不能说

1. **不能说 50.8 秒是实测。** 报告里写了"解析估算"，讲了实测被戳穿比一开始就说清楚亏得多。
2. **不能说"全部完成"。** 固件的脉冲、限位、StallGuard 配置还没上板，只有骨架。
3. **不能用"首创""填补空白"。** 规则明确不认这个，反而招质疑。
4. **不能说非自己实现的部分是自研。** 步进驱动芯片、OpenCV、StallGuard 都是现成的。

## 五、如果评委要看代码

仓库 `github.com/jiangyuyue111/smart-sorting`（私有，需要可以给看）。

现场只需要展示两个东西，别的一概不用翻：

```powershell
python -m sorting.app.demo
```
→ 打开 `out\demo\report.md`，翻到**第 0 节那张来源表**。这是全场最有说服力的一页。

```powershell
python -m sorting.app.main --demo --inject-skip 2 5
```
→ 现场跑，让它"抓空"两件，证明失败分支是真的能跑的，不是 PPT 上画的。
