## 0. 一页纸

**两颗芯片，四条接口，一层仿真。**

```
┌─────────────────── 树莓派 4B · Linux（非实时，只做决策）───────────────────┐
│                                                                            │
│  采图 ──▶ 单应 ──▶ 分割 ──▶ 特征 ──▶ 分类 ──▶ 排程 ──▶ 序列 ──▶ 屏幕      │
│  (开赛前一次)                              │                  │            │
└────────────────────────────────────────────┼──────────────────┼────────────┘
                                             │ UART 115200      │ SPI
                                             │ 文本行协议        ▼
┌────────────────────────────────────────────▼──────────────┐  480×320
│            STM32F407（实时，只做脉冲 + 堵转检测）           │  ST7796S
│  梯形加减速 → STEP/DIR · 限位回零 · StallGuard · 看门狗     │
└────────────────────────────────────────────────────────────┘
```

**三个决定了这套软件形状的选择：**

| 选择 | 一句话理由 |
|---|---|
| **上电时把识别一次做完**，开赛后不再碰相机 | 视觉永远不可能成为比赛中的停顿源；相机挂了还有时间重启 |
| **夹爪用堵转位置判断"夹到没有"**，不加传感器 | TMC2209 的 StallGuard 本来就报位置，省一路 IO 和一根线 |
| **没有硬件也能跑完整一轮** | 硬件在装、在坏、在别人的机台上时，软件仍然可以开发、测试、演示 |

## 1. 为什么是"树莓派 + MCU"两颗芯片

树莓派跑 Linux，加 Python 解释器，GIL 和调度抖动让它在毫秒级上不可信；
但它的相机、OpenCV、屏幕都现成。STM32 相反：没有文件系统，但定时器输出
脉冲是硬件级的。

分工就按这个来——**树莓派只决定"去哪"，STM32 只决定"怎么走到"**。
插补、加减速、限位、堵转全在 MCU 侧，串口只传目标位置。

这条分工的副产品是：树莓派进程崩了，MCU 还活着，可以继续做微动作，
不会被 15 秒无动作判死。

## 2. 运行架构

单进程三线程。不拆多进程——共享一份只读任务队列的收益远大于隔离收益。

| 线程 | 职责 | 绝对不做 |
|---|---|---|
| **main** | 唯一的串口写入方；跑动作序列 | 不做图像处理、不渲染 |
| `display` | 读当前显示模型，自己节流刷屏 | 不阻塞主线程 |
| `watchdog` | 空闲时 ping MCU，连续 3 次失败置 FAULT | 不直接操作硬件 |

**为什么串口只给主线程**：串口是一问一答的半双工链路，两个线程同时写会把
`GOTO 30.0 40.0` 和 `GRIP 6.0` 拼成一条非法指令。这类偶发故障最难查，
所以从结构上禁止——`Session` 只被 main 线程调用。

**为什么屏幕独立成线程**：渲染一帧 480×320 在树莓派上约 10~30 ms，
放在主循环里会直接吃掉节拍。屏幕晚 200 ms 没人看得出，运动晚 200 ms 就是丢件。

## 3. 模块划分

完整目录和每个模块的职责见 [`sorting/README.md`](../sorting/README.md)。
这里只讲分层的原则：

```
core/     不认识视觉，也不认识屏幕 —— 只认"目标点"和"指令"
vision/   只认图像和毫米 —— 输出 (cx_mm, cy_mm, 类别, 置信度)
display/  只认数据 —— 输入一个 DisplayModel，输出一张图
app/      把上面三层接起来，管线程、状态机、异常兜底
```

`core` 和 `vision` 之间只有一个数据结构（`Detection`），`core` 和 `display`
之间只有一个（`Target` / `DisplayModel`）。换视觉算法不用动运动代码。

## 4. 接口契约

### 4.1 串口协议

一行一条，ASCII，`\n` 结尾，空格分隔。上位机是唯一写入方。

| 方向 | 帧 | 含义 |
|---|---|---|
| ↓ | `GOTO <x> <y>` | 绝对 XY（mm，一位小数） |
| ↓ | `Z <mm>` | 绝对 Z |
| ↓ | `GRIP <mm>` | 夹爪张合轴绝对位置（0 = 全闭，40 = 全张） |
| ↓ | `HOME` | 四轴回零 |
| ↓ | `STOP` | 立即中止 |
| ↓ | `PING` | 存活探测 |
| ↑ | `OK` / `DONE` / `PONG` | 应答 |
| ↑ | `GRIPD <mm>` | 夹爪**实际停止位置**（异步） |
| ↑ | `ERR <code> <text>` | 故障 |

错误码：`E01` 超行程、`E02` 回零找不到限位、`E03` 未知指令、`E04` 夹爪超时。

设计约束：只传"到哪"，不传插补参数；每条指令必须有 `OK`，运动类还要有
`DONE`，上位机据此做超时判定；解析不出的行直接丢弃并计数，不抛进主循环。

### 4.2 夹爪怎么知道夹到了

TMC2209 的 StallGuard 让电机堵转即停。空夹时爪口会一直合到 `grip_close_mm`；
夹到工件时会停在工件宽度处，位置明显更大。于是：

```
GRIPD ≥ grip_hold_min_mm  →  夹到了，去料盒
GRIPD <  grip_hold_min_mm  →  空夹，抬起来直接跳过，不往料盒跑
```

这是**位置判据**，不是力度判据。夹太紧会压坏件，所以力矩上限在 MCU 侧限死。

### 4.3 屏幕

赛规把显示当计分项：每件必须显示**序号 / 名称 / 图片 / 总数**，
错一项这件不得分，且每分拣一件后必须刷新。

`display/renderer.py` 输出 480×320 的 PIL Image，真机上 `img.tobytes()`
直接喂 SPI 屏。布局、字号、配色在 PC 上就能全部调完——这是把屏放在 MCU
而不是单板机上的最大好处：所见即所得。

## 5. 单件时序

```
GRIP_OPEN → GOTO(取点) → Z(取件高度) → GRIP_CLOSE → 稳定
          → 读 GRIPD
              ├─ 夹到 → Z(安全高度) → GOTO(料盒) → Z(放件) → GRIP_OPEN → Z(安全高度)
              └─ 空夹 → Z(安全高度) → 直接 DISPLAY（标 NG）
          → 刷新屏幕 → 下一件
```

两个细节：

- **先张开再移动**。带着闭合的爪子横移会刮到旁边的工件，一次就能把整盘毁掉。
- **失败也要刷新屏幕**。跳过不是"什么都不做"，屏上必须能看到这件被判为 NG，
  否则评委看到的是停在上一件。

## 6. 视觉链路

```
V 通道 Otsu → 形态学 → findContours → 单应(像素→毫米) → 抽稀 → 特征 → 分类
```

### 6.1 为什么不能用背景差分

赛规要求工件事先摆好、不允许触碰整理。这意味着**拿不到"空托盘"这张参考图**，
背景差分从根上不成立。所以用明度通道的 Otsu——彩色塑料件的 V 高，深灰哑光
托盘的 V 低，两峰拉得很开，自动找谷底比手调阈值稳。

### 6.2 为什么要抽稀

原始像素轮廓是锯齿状阶梯线，周长被高估约 5%。实测一个标准正方形会算出
圆度 0.73（理论 0.785），圆会算出 0.88（理论 1.0），三个形状挤在一起就没法分。

用 1% 周长的 Douglas-Peucker 抽稀后，正方形和三角形直接回到理论值
（见 `tests/test_vision.py::test_circularity_recovers_theory`）。这不是调参
凑结果，是把像素离散化带来的偏差去掉。

### 6.3 分类判据

赛规的判据是"**形状相同且颜色相同**"，所以分类拆成独立的两步：

| 步骤 | 特征 | 说明 |
|---|---|---|
| 形状 | 圆度 `4πA/P²` | 圆 1.000 / 方 0.785 / 三角 0.605，间隔大且可解释 |
| 颜色 | 色相直方图**峰值** | 红色跨 0°/180°，求均值会算成青色 |

组合成类别后还要过两道闸：`confidence ≥ min_confidence` 且
`d₂ - d₁ ≥ min_margin`。任何一道不过就返回 `None`，该件走 SKIP——
**宁可少抓一件，不能把错的扔进对的盒子**。

阈值全在 `config/classes.json` 里。现场换货只需要重新填形状特征和色相区间，
不用改代码——这是"决赛现场能临时调"的前提。

### 6.4 视差

相机不是正交投影，工件有高度，会在图像上产生径向偏移：

```
X_true = X_meas · (1 - h/Hc)      Y_true = Y_meas · (1 - h/Hc)
```

h 是工件高度，Hc 是相机到托盘的高度。当前 h≈0（薄片），补偿量可以忽略；
换成有厚度的物料时必须启用。

## 7. 排程

赛规只要求"同形同色进同一个盒子"，**不要求同类连着做完**。所以排程是自由的
旅行商问题，不该先入为主地按类别分组。代码里三种排法都真算一遍取最短：

| 策略 | 说明 |
|---|---|
| `detect` | 按检出顺序（对照基线） |
| `nn` | 全局最近邻，不管类别 |
| `class` | 同类一次做完，类别间 6! = 720 全排列穷举 |

三者用同一个代价函数（当前点 → 取点 → 料盒 → 下一个取点）算，数字可比。

**当前实测（合成场景 12 件，seed=0）：`detect` 3576 mm → `nn` 3364 mm，省 5.9%。**

> 降幅不大是有原因的：单件路径里取点→料盒那一段（约 200 mm）是固定的，
> 排序只能优化取点之间和料盒之间的移动。所以排序在这里是"顺手拿到"的收益，
> 真正的节拍杠杆在 §8。

## 8. 节拍

> ⚠ 下面全部是**按齿轮传动公式解析算出**的，不含加减速、回程间隙、相机曝光。

12 件一轮（seed=0）：**约 50.8 s**，含开机回零 6 s。

| 轴 | 累计行程 | 累计运动时间 | 占比 |
|---|---|---|---|
| X | 3319 mm | 16.6 s | 40% |
| Y | 750 mm | 3.8 s | 9% |
| Z | 1885 mm | 18.8 s | **45%** |
| GRIP | 383 mm | 6.4 s | 15% |

（各轴时间之和大于总时长，因为 XY 是联动的。）

**Z 轴是瓶颈，不是 XY。** 每件工件 Z 要上下各两次，而 Z 速度只有 100 mm/s，
比 XY 慢一半。180 s 的预算目前看很宽裕，但真正的优化方向是：

1. 把 `z_safe_mm` 从 45 mm 降到夹爪实际长度允许的最小值（最直接）
2. 提高 Z 轴速度（实测不失步的最高速）
3. 用"抬高到下料高度 + 水平让位"替代"抬到全局安全高度"

这三条的实测数据都要等装配完成（见 §11）。

## 9. 容错优先级

**不停住 > 不放错 > 多完成。**

写任何一处逻辑时先问：它崩了会不会让装置停住？

| 故障 | 处理 |
|---|---|
| 某件识别不出 | SKIP，继续下一件，屏幕标 NG |
| 某件空夹 | SKIP，抬起，不往料盒跑 |
| 夹爪不回 GRIPD | 超时 → 抬 Z → SKIP（不整个停机） |
| MCU 报 ERR | 停机进 FAULT，屏幕显示"
故障 |
| MCU 失联 | 看门狗连续 3 次 ping 失败 → FAULT |
| 任何未捕获异常 | 顶层兜底 → 发 STOP → FAULT |

`E04 GRIP_TIMEOUT` 特意不当作致命错误：夹爪没走到位大概率是件被卡住，
抬起来跳过就好，为此停掉整台机器不划算。

## 10. 可测性

这是本方案最花力气的地方——**所有东西都能在没有硬件的情况下验证**。

| 模式 | 命令 | 验证什么 |
|---|---|---|
| 单元测试 | `python -m unittest discover -s sorting/tests -t .` | 91 个测试，无板无相机 |
| 完整演示 | `python -m sorting.app.demo` | 合成场景 → 报告 + 屏幕帧 + CSV |
| 流程演练 | `python -m sorting.app.main --demo` | 状态机 + 看门狗 + 线程模型 |
| SKIP 分支 | `--inject-skip 2 5` | 人为空夹，验证 NG 路径 |
| 真机 | `--port COM3 --calib calib.json --image tray.png` | 换掉图和 H，下游代码不动 |

**关键点**：合成侧和检测侧不共享任何中间量。检测只拿到一张图和单应矩阵，
和真机拿到的信息一样多。所以合成图上测出来的误差是有意义的下界参考。

| 项 | 状态 | 说明 |

| STM32 固件（HAL） | ⚠ 骨架 | `main_stm32.c` 只过了语法检查，脉冲/限位/StallGuard 等上板 |
| SPI 屏驱动 | 未写 | `renderer.render()` 返回 PIL Image，树莓派侧写 spidev 即可 |
| 视差补偿 | 未启用 | 薄片可忽略；换厚件必须开 |

标定为什么必须先标内参：单应只在无畸变图像上成立。本方案是 250 mm 工作
距离 + 小焦距镜头，画面边角的桶形畸变会让托盘四角外扩几个百分点——而那正好
是工件所在的位置。先标内参去畸变再解单应，四角才准。

求解器自检（无噪声）：托盘内最大偏移 **7.6×10⁻¹¹ mm**，说明求解链路本身没算错。
四角各带 1 px 手点误差时，托盘内最大偏离 **0.74 mm**——这是手点四角的精度上限，
要再准就得用标记板或者多点拟合。
